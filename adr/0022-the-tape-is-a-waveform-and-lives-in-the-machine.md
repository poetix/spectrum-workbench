## Context

A Spectrum tape is an audio signal. The machine's whole view of it is bit 6 of
a port `0xFE` read, and the loading routine sits in a loop timing how long that
bit stays where it is. Nothing on the machine can see a byte, a block or a
checksum; those are conclusions the loader draws from intervals.

There are therefore two ways to make a tape image load, and they are not
alternatives so much as different features.

**Replay the waveform.** Turn the file into pulses and drive `EAR` with them.
Every loader ever written works, because what runs is the loader.

**Trap the ROM routine.** Notice the program counter arriving at `LD-BYTES`,
put the block in memory, set the flags and return. It is instant, and it works
for exactly the software that uses the ROM loader — which excludes most
commercial releases, all of which shipped custom loaders precisely because the
ROM's was slow. A trap is also invisible when it fails: the tape simply never
loads, with no indication that the program was never going to call the routine
being trapped.

So the waveform is the mechanism and the trap is a convenience on top of it,
and the order they were built in matters — the other way round produces
something that appears to work and cannot be extended into something that does.

The second question is where the state goes. ADR-0021 put the beeper *outside*
the machine, on the argument that host state and wall-clock time must stay out
of anything ticket 0027 will checkpoint. A tape looks superficially similar —
it is a file, it is I/O, it produces a signal — and the answer is the opposite.

ADR-0017 already said so in its table: tape *edges* are regenerated by the
emulation thread rather than crossing the command ring, because "the edge
schedule is a pure function of the tape data and the T-state at which transport
started, which the emulation thread can compute for itself". Regenerating them
means holding the position they are regenerated from.

## Decision

### The tape deck is machine state; the recorder is not

`Spectrum` gains a `Tape`: an `Arc<Tap>`, a player position, the T-state the
pulse in progress ends at, and the level it put on the line. Forty bytes and a
pointer.

The distinction against the beeper is not I/O versus not-I/O, it is whether the
machine's own behaviour depends on it. A load in progress *is* machine state:
the loader is in the middle of timing a pulse, and a checkpoint restored
without the tape position resumes into a measurement of a waveform that is no
longer playing — a machine that diverges for reasons ticket 0029 would report
as a mystery. A save in progress is an output. Restoring past one loses a
partial block, and the symptom is a file that is visibly short.

Size settles what is left. A block being recorded is up to 64 KB; a checkpoint
ring holding a machine per emulated second would pay that in every entry, to
preserve something nobody can step backwards into.

### The image is shared, immutable, and named by content

`Arc<Tap>`, so cloning a machine into a checkpoint costs a pointer rather than
a copy of the tape, and `Tap::hash` is the FNV-1a over the file that ADR-0017
asks a recorded session to name its tape by. Mounting allocates and parses,
which is why it happens at the rate a person mounts tapes and not on the
emulation thread.

### Edges are scheduled events

`Machine::next_event` returns the earlier of the frame interrupt and the next
tape edge, and `service_event` handles whichever was due. A running tape puts
an event every few hundred T-states — about 2 kHz, against a control tick at
16 kHz — and a stopped one costs a branch.

The alternative, computing the level from the tape position at the moment of
each port read, is exact rather than merely close, and was rejected: it puts
the tape into the bus's hot path for every `IN` a program makes, and it cannot
drive anything that is not a read of `EAR`, which the audible loading noise a
real machine makes through its own speaker eventually will be.

The cost of scheduling is that an edge lands late by however far the last
instruction overran its deadline — up to twenty-odd T-states, against a data
pulse of 855 and a ROM threshold with hundreds of T-states of margin. What
matters more is that it is not cumulative: each pulse is added to the edge that
was *due*, not to the clock that arrived, so a thousand late edges are still a
thousand pulses long in total.

### `service_event` now has to say what it was woken for

It used to mean "the frame ended", and two wrappers were built on that
assumption. `Spectrum::frame_due` is the question they now have to ask: the
beeper renders a frame of sound when the frame is what came due, not when a
tape pulse was. Getting this wrong is a frame of samples per pulse — audible
immediately, but only when a tape is running, which is not where anybody would
look.

### Saving reads the ULA's `MIC` edges, in a wrapper, off the emulation thread

ADR-0021 put a `MIC` bit in the edge log because it feeds the same amplifier as
the speaker. It is also what a saving program writes, so the save path is the
beeper's path with a different consumer: `Saving<M>` wraps a machine, drains
the frame's `MIC` transitions before the log rolls on, and decodes pulses back
into blocks. `Saving<AudioMachine>` and `Saving<Spectrum>` are both machines,
so the stack composes in whichever order a front end wants.

It is a signal decoder rather than a trap on `SA-BYTES`, for the same reason
loading is: a program that writes its own saver never calls the ROM.

Its buffers are fixed and it discards rather than truncates. A block that
overran the buffer, or stopped in the middle of a byte, or contained a pulse
that was neither a zero nor a one, is thrown away and counted. A short block
written into a TAP file is a corrupt tape that looks fine until somebody tries
to load it, which is the one outcome worth going out of the way to avoid.

### The formats are a crate that cannot name a Spectrum

`rkw-tape` holds TAP parsing, the pulse schedule and the decoder, and depends
on nothing — the same boundary, and for the same reason, as `rkw-audio`
(ADR-0021). Pulse lengths arrive as a `Timing` struct rather than as constants,
which is what ticket 0017's TZX needs (it carries its own timings per block)
and what lets the arithmetic be tested at numbers small enough to check on
paper.

## Consequences

**Positive:**

- Custom loaders will work, because what runs is the loader. That is most of
  the commercial catalogue, and it is not something a trap-based design can be
  extended into.
- The ROM validates the waveform. `tests/tape.rs` calls the real `LD-BYTES` at
  a played tape and types `LOAD ""` at the BASIC prompt, which checks the pulse
  timings against sixteen kilobytes of code that has an opinion about every
  edge.
- Saving and loading check each other: what the ROM's `SA-BYTES` writes is
  recorded, written out as a TAP, mounted, and loaded back by the ROM.
- A load in progress survives a checkpoint, so ticket 0028's reverse execution
  works across one.
- 0017's TZX is a second `Timing` and a second source of pulses, not a second
  design.

**Negative:**

- `service_event` fires about forty times more often with a tape running, and
  each call walks a small state machine. It is nothing against 350× real time,
  but it is not nothing against a slice loop that was designed around fifty
  events a second.
- Mounting and starting a tape are direct calls on the machine and are *not* in
  the command log yet, so a session that loads a tape does not replay. The
  command record is sixteen bytes and cannot carry a path; widening it, or
  naming the tape by the hash that already exists, belongs with ticket 0026,
  which is where log integrity lives.
- A checkpoint restored in the middle of a save loses the partial block, in
  exactly the way it loses the beeper's filters.
- Two wrapping machines now exist, and each carries a full delegation of `Bus`.
  Ticket 0020's contention will have to be added to `Spectrum` and to nothing
  else, which is what ADR-0002 promised, but the delegations have to stay
  honest for that to hold.

**Caveat:**

The `EAR` line is not fed back into the speaker, so loading is silent. On a
real 48K machine the tape signal reaches the amplifier and the loading noise is
how a person knows the tape is working. Adding it means a third level in the
edge log and a fourth term in the mixer, and it belongs with the front end that
would let anybody hear it.
