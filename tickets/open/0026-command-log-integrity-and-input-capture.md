## Summary

Make the recorded command log trustworthy enough to build reverse execution on
(ADR-0017): report its own truncation, be readable while the machine runs, and
capture every input the emulation thread could not have worked out for itself.

## Acceptance criteria

- [ ] Log drop count, surfaced next to `Emu::log`, incremented when a command is
      applied but not recorded
- [ ] `Emu::replay` refuses a log known to be incomplete rather than returning a
      machine that is quietly wrong
- [ ] The log is readable from `Handle` while the machine runs, without stalling
      the emulation thread and without allocating on it
- [ ] The input taxonomy of ADR-0017 documented in `command.rs`: what crosses
      the ring, what stays in `next_event`, and why
- [ ] Keyboard input (0013) is a `Command`, applied at a control tick
- [ ] Tape transport — mount, play, stop, seek (0016/0017) — is a `Command`;
      tape edges are not, and are regenerated by the machine's scheduler
- [ ] Mounted artefacts (tape, ROM) referenced in the log by content hash
- [ ] `replay` verifies artefact hashes and refuses on mismatch, naming the
      artefact
- [ ] A recorded session that loads from tape and types at the keyboard replays
      to an identical machine — registers, memory and clock

## Notes

Depends on 0009 (closed): the log, the stamping and `Emu::replay` are there, and
this ticket is what makes them dependable.

This is deliberately ahead of 0013 and 0016. Both add an input path, and the cost
of routing an input correctly while it is being written is near zero; the cost of
discovering afterwards that replay diverges — with no visible cause, arbitrarily
far from the input that caused it — is not.

The truncation gap is the sharp one. `emu.rs` stops recording when the log is
full and says nothing, which is exactly the failure the ring refuses to have:
"a gappy trace presented as a whole one is a lie" (`ring.rs`). A truncated log
replays to a different machine and looks complete.
